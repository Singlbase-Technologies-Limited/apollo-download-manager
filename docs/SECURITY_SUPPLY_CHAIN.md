# Security: supply chain

How known advisories in Apollo Download Manager's dependencies are found, judged and recorded. The rest of the security design is in [SECURITY.md](SECURITY.md); split from it by #425.

## Dependency advisories (#75)

Apollo Download Manager ships native libraries and many crates and npm packages, and advisories against them are published every week. How Apollo Download Manager finds them and what it does (PO decisions on #75):

- **The check:** `pnpm check:advisories` runs cargo-deny 0.20.2 (`cargo deny --locked check advisories`, configured in [`deny.toml`](../deny.toml)) against [`Cargo.lock`](../Cargo.lock) and the RustSec database, and `pnpm audit --audit-level moderate` against [`pnpm-lock.yaml`](../pnpm-lock.yaml). It fails on a vulnerability, on unsound code anywhere in the graph, on an unmaintained crate Apollo Download Manager depends on directly, and on an npm advisory rated Medium (npm's "moderate") or higher, unless the advisory is accepted below. A yanked crate is a warning. cargo-deny is a developer tool, installed with `cargo install cargo-deny --locked --version 0.20.2` ([DEPENDENCIES.md](DEPENDENCIES.md)).
- **When it runs:** weekly, Mondays 04:00 UTC, in [`advisories.yml`](../.github/workflows/advisories.yml), and by hand (`gh workflow run advisories.yml`); at least before each release candidate.
- **Native libraries** aren't in either lockfile, so they are watched by hand, at each check and before each native update ([BUILDING_NATIVE.md](BUILDING_NATIVE.md)): curl ([vulnerability table](https://curl.se/docs/vulnerabilities.html)), nghttp2, zlib and OpenSSL (the versions in [`scripts/native/deps.lock`](../scripts/native/deps.lock)), libtorrent with Boost and OpenSSL from vcpkg (#62), and SQLite, which `libsqlite3-sys` bundles (RustSec covers the crate, not every SQLite CVE). The WebView (WebView2 on Windows, WebKitGTK on Linux) is the operating system's and is updated with it. russh is a crate, so RustSec covers it.
- **Dependabot** opens security-fix PRs for Cargo and npm, and no routine version updates. Each is an ordinary PR the PO reviews.
- **Dependabot PRs need their notices regenerated by hand** (PO decision on #255). Dependabot changes the lockfiles but not [`THIRD_PARTY_NOTICES.md`](../THIRD_PARTY_NOTICES.md), which lists each component's version, so CI's `check:notices` fails before the code checks run. The agent, or the PO, makes a branch of its own from the latest `main` with the same update, runs `pnpm notices`, and opens it as an ordinary PR. Dependabot's PR is then closed, pointing to it. Dependabot's branch can start from an older `main`, so its lockfile isn't copied: the update is applied to the current one.
- **Assessing one:** each advisory that affects a locked or native dependency gets an issue from the "Advisory assessment" template: where the dependency comes in, on which platforms, whether the affected code is built in and reachable, and whether it ships or is only a development tool. Then it is fixed, or accepted with its reason in [`deny.toml`](../deny.toml) (or, for npm, `auditConfig.ignoreGhsas` in [`pnpm-workspace.yaml`](../pnpm-workspace.yaml)) and in the register below.
- **Response times,** from the day the advisory is published or found, whichever is later, to a fix merged or an accepted assessment: **Critical 2 days, High 7 days, Medium 30 days, Low with the next release.**
- **Release blocker:** an unfixed advisory rated Medium or higher that affects a feature Apollo Download Manager enables blocks a release or release candidate ([APPROVED_DEPENDENCIES.md](APPROVED_DEPENDENCIES.md#release-blockers-related-to-provenance)).
