# Security

How Apollo Download Manager protects downloads and the people who use it. The rules every contributor follows are in [AGENTS.md](../AGENTS.md#security-and-data) and [`.claude/rules/security.md`](../.claude/rules/security.md). This document records what Apollo Download Manager does and what was measured. It covers TLS, links and redirects, the browser bridge, FTP, SFTP host keys, secrets, files and folders, dependency advisories and the proxy.

Dependency advisories are in [SECURITY_SUPPLY_CHAIN.md](SECURITY_SUPPLY_CHAIN.md).

Security towards servers and the network (TLS, FTP and FTPS, SFTP host keys, mirrors, Metalink, the proxy) is in [SECURITY_NETWORK.md](SECURITY_NETWORK.md).

## Links, redirects and local addresses (#67)

Links come from users and from web pages, so each is checked before it reaches the engine, and every request the engine makes is held to an allowlist.

- **Checking a link** (`request::normalize_link`, on every link the Add path takes): a space or a control character is refused with `INVALID_URL`, as V1 refused it. A link longer than 8 KiB is refused, and so is a login in the link, which has its own fields (#40). An international domain name is turned into its ASCII form, so `https://bücher.example/` is stored, shown and requested as `https://xn--bcher-kva.example/` (PO decision on #67, with the `url` crate's IDNA). A look-alike name therefore shows as what it is. Other characters outside ASCII are percent-encoded.
- **Protocols:** every libcurl request allows only `http`, `https`, `ftp` and `ftps` (`CURLOPT_PROTOCOLS_STR`), and a redirect only `http` and `https` (`CURLOPT_REDIR_PROTOCOLS_STR`). Apollo Download Manager follows redirects itself and checks each one first (`redirect.rs`): a redirect to `file://`, `scp://`, `sftp://` or any other protocol is refused before anything is connected (tested against the local server; CVE-2026-86410 was a redirect to SFTP in the curl tool). At most 10 redirects are followed. SFTP links go to Apollo Download Manager's own SFTP layer, never through libcurl.
- **From `https` to `http`:** a redirect that would leave TLS stops the download with "The server redirected to an insecure http:// address on `<host>`…", and the details panel offers **Continue over http** (PO decision on #67). Choosing it allows the downgrade for that download only, is stored with it, and retries it. The login and custom headers still don't follow, since `http` is another origin. Tested against the local TLS fixture, with and without the confirmation.
- **Local addresses** ([ADR-0006](decisions/0006-browser-links-to-local-networks.md)): a link the browser extension sent (`AddRequest.fromBrowser`) that connects to this computer or a private network stops before its request is sent, and the details panel shows the address it really leads to, with **Download anyway**. Choosing it allows local addresses for that download only, is stored with it, and retries it. Local means loopback, private (RFC 1918), shared (RFC 6598), link-local, unspecified and IPv6 unique-local addresses, also when mapped into IPv6. The check is on the address libcurl actually connected to (`CURLOPT_PREREQFUNCTION`), after the name was resolved, so a name that resolves to a local address, as in DNS rebinding, is caught too (tested with `localhost`). Typed and pasted links are never checked.
- **No ambient configuration:** proxy variables such as `http_proxy` are ignored, because every request sets an empty proxy (ADR-0008; the proxy feature is #192), and `.netrc` support is compiled out of Apollo Download Manager's libcurl ([`scripts/native/build.mjs`](../scripts/native/build.mjs)). Both are tested in their own test binaries, which set the variables and a `.netrc` with a login and check the request went direct and without it.
- **Logs:** a refused redirect's message names no URL, which may hold a token; the libcurl layer never logs one.

## The browser bridge (#65)

Messages from the browser are untrusted, and reach the app only through Apollo Download Manager's own native host ([BROWSER_EXTENSION.md](BROWSER_EXTENSION.md#the-native-host)):

- **Only Apollo Download Manager's extensions:** the host and the app accept only Apollo Download Manager's Chrome extension origin and Firefox add-on ID. V1's are refused (tested).
- **Checked twice:** the host checks each message against the protocol's allowlist (three commands; no paths, headers, cookies or engine options; at most 64 KiB), and the app checks it again.
- **Authenticated:** the app writes a per-launch token (32 bytes from the OS's secure random source) where only this user can read it, and refuses an envelope without it (compared in constant time). The Windows pipe is created first and refuses remote clients; the Unix socket is owner-only.
- **Bounded:** at most 8 connections at once, 15 seconds each, a line of at most 72 KiB, and 30 messages in 10 seconds.
- **The user decides:** by default a link only opens the Add dialog, and torrents always do. A link added at once is marked as from the browser, so a local address waits for the user ([above](#links-redirects-and-local-addresses-67)).
- **Registration** is per user, and never touches V1's: every file and registry key is named after Apollo Download Manager's host, and unregistering removes only a plain file that names Apollo Download Manager's host.

## Adding downloads (#60)

Everything the Add dialog sends is checked again natively (`Manager::add_request`); the dialog's own checks are for usability. What protects Apollo Download Manager:

- **A login never goes in a link.** A link with one is refused (`INVALID_URL`); the login has its own fields and stays in memory, as do custom headers and a key's passphrase.
- **`.torrent` files are read only as plain files:** an absolute path, never a link, at most 16 MiB, parsed by Apollo Download Manager's own bounded parser before the torrent helper sees it. Files dropped on the window reach Rust, which passes the page only plain `.torrent` files, at most 500; the manager checks each again when it is added.
- **A chosen folder is created only when the user agrees,** inside its nearest existing parent, one level at a time, never through a link.
- **Fetched `.torrent` links** go through the transfer engine with its usual TLS checks, into the app's own `torrent-links` folder, at most 16 MiB and 60 seconds. What arrives must parse as a torrent. It is kept without its trackers, whose addresses can carry a private tracker's passkey; they stay in memory, as every torrent's do (PO decision on #58). When the app starts, it deletes any plain file in that folder that no download comes from, and touches nothing else there.
- **SFTP host keys** are confirmed by the user in the window, after the download stops before logging in (below). A changed key is only explained, never offered for trust.
- **A login given again** (`set_download_login`, #59), for a download that came back after a restart without it, is checked as the Add path checks it (`TransferSpec::check_request`): its headers, its login, and that an SSH key is for an SFTP link with a user. An invalid one is refused whole, and the download keeps waiting for it. It stays in memory, as when the download was added.

## Secrets (#70)

Logins, custom header values (cookies, tokens) and SSH key passphrases are secrets. What Apollo Download Manager does with them:

- **Held as `Secret`s** ([`crates/velocity-core/src/secret.rs`](../crates/velocity-core/src/secret.rs)): overwritten in memory when dropped (`zeroize`, PO decision on #70), and never shown by `Debug` (tested). The contract's JSON doesn't change: a secret crosses the window's commands and the engine's pipe as its plain string, in memory. The engine copies the login out as plain strings for the libcurl and SFTP layers, for the transfer's life only. Those copies, and the ones libcurl and russh keep while a transfer runs, are not wiped by Apollo Download Manager.
- **Never written** to the database, a checkpoint, a temporary file, the app's log, the diagnostics export, or a child process's arguments or environment. The leak test ([`crates/velocity-transfer/tests/secret_leaks.rs`](../crates/velocity-transfer/tests/secret_leaks.rs)) adds downloads with an HTTP login and cookie and an FTP login through the real child engine, and SFTP key and password logins, pauses one so a checkpoint is stored, then runs the shared secret-leak scan (#71, [TEST_FIXTURES.md](TEST_FIXTURES.md#the-secret-leak-scan-71)) over every file the test's folders hold (WAL included, open and after closing), temporary files, the app's log and the diagnostics export, after logging each download's record (the core itself logs nothing while a download runs). On Linux it also reads the running engine's arguments and environment; everywhere it checks the child is started with only `serve` and the few kept variables. A private tracker's passkey gets the same scan through the torrent helper ([`crates/velocity-torrent/tests/manager.rs`](../crates/velocity-torrent/tests/manager.rs)). The SFTP password part runs where a password server is provisioned (CI's Linux runner); elsewhere it says NOT RUN, as the SFTP engine tests do.
- **The system keychain, on consent only** ([ADR-0015](decisions/0015-keychain-with-consent.md)): "Remember this login in the system keychain", unticked by default, saves that download's login, headers and key passphrase as one entry under Apollo Download Manager's own service name (`<identifier>.logins`), through the `keyring` crate: Windows Credential Manager, or the Secret Service on Linux. After a restart the download gets them back from there; removing it deletes the entry. A keychain that is missing or refuses is said (`KEYCHAIN_UNAVAILABLE`), and nothing is saved. A saved login is checked again, as when it was added, before it is used.
- **After a restart, without a remembered login,** a download that had one waits for it again, with a note (V1's behaviour, #58).
- **A torrent's trackers, on consent only** ([ADR-0021](decisions/0021-tracker-passkeys-in-the-keychain.md), #472): a private tracker's address carries a passkey. "Remember this torrent's trackers in the system keychain", unticked by default, saves them in the download's own keychain entries (`<id>.trackers` and its parts), never in the database, resume data or logs (tested: the manager's tests look for the passkey in the stored records). Removing the download deletes them.

## Files and folders (#72)

Names come from links, servers (`Content-Disposition`), browsers, torrents and Metalink documents, so they are untrusted; and the folder a download writes to may hold other programs' files, V1's included. What Apollo Download Manager does:

- **One set of checks** ([`crates/velocity-core/src/fs_safety.rs`](../crates/velocity-core/src/fs_safety.rs)), shared by the engine's part files, Metalink folders, download removal, torrent deletion and the database: whether something is a link, a plain file or a plain folder (read without following it), whether a path is inside its folder by its names alone, and whether it is reached only through plain folders.
- **What a link is:** a symbolic link, or on Windows a junction or a mount point, which redirect to another place. Other Windows reparse points, such as the files of a cloud-sync folder, are ordinary files (PO decision on #72).
- **Names stay in the folder:** a name with `..`, a separator, a drive, a reserved Windows device name (`CON`, `con.txt`, `COM1` to `COM9`, `LPT1` to `LPT9`, `CONIN$`…), a control character or a part file's suffix is refused where it is given (`naming::check_file_name`; the engine checks every spec again), and renamed predictably where Apollo Download Manager picks the name (`CON.txt` becomes `_CON.txt`, `../../x.sh` becomes `x.sh`). A path that climbs out with `..` is never inside its folder, whatever is on disk (a regression test: torrent deletion once compared only the start of the path).
- **Nothing through a link:** part files are created only where nothing exists (`create_new`), reopened with `O_NOFOLLOW` or `FILE_FLAG_OPEN_REPARSE_POINT` and checked again on the open handle, and folders are created one level at a time, refusing a link in the way.
- **No overwrite:** a finished file is renamed into place without ever replacing an existing file (`renameat2` with `RENAME_NOREPLACE` on Linux, `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` on Windows), so a file that V1 or anything else wrote at that name meanwhile is kept (tested). Names that look alike but are stored differently (é as one character, or e and a combining accent) are two files, as Windows and Linux treat them; names are not normalised (PO decision on #72), and finishing one never replaces the other (tested). A name differing only in case is the same file on Windows, so it is refused there and kept.
- **Mark of the Web (#469):** on Windows, a finished direct download gets a `Zone.Identifier` stream with `ZoneId=3` and only the link's origin as `HostUrl`, as browsers write it, so SmartScreen and Office's protected view still treat it as from the internet (`fs_safety::mark_from_internet`, tested). It's written only on a plain file, never through a link. A file system without streams (FAT32, exFAT) can't hold it; the download is kept, and the engine logs a warning. A completed torrent's files are marked the same way, with the zone only, since a torrent has no web address: only its wanted, whole files, at paths inside the torrent's folder reached through plain folders (`finished_files` in [`crates/velocity-torrent/src/engine.rs`](../crates/velocity-torrent/src/engine.rs)), so a name in a torrent's metadata never leads the mark elsewhere. libtorrent's own `.parts` file isn't marked. A failure is logged by the torrent helper, and the torrent stays completed.
- **Long paths:** a folder deeper than Windows' old 260-character limit works: the finishing rename passes a verbatim path (`\\?\C:\…`), as the standard library's own calls do (tested with a path over 300 characters).
- **Deleting only what a download owns:** removal deletes a direct download's file and part file, and a torrent's files and the folders it made, each only if it is a plain file no larger than the download says, reached through plain folders inside the download's folder. A link at a file's name, or a download folder that has become a link, deletes nothing (tested with a junction on Windows).
- **Owner-only data:** on Linux the database, its WAL and shared-memory files (which hold the checkpoints) and its backups are `0600` (tested).
- **How the link tests run:** junctions need no rights on Windows, so folder-link cases always run. A file symbolic link needs Developer Mode or an administrator there; without either, those cases print NOT RUN (PO decision on #72). On Linux every case runs.
